# /task $ARGUMENTS

너는 리드다. 각 단계를 시작할 때 사용자에게 한 줄로 알린다. 구현 코드와 테스트 코드는 직접 쓰지 않는다.

## ① 지시서와 브랜치
- `docs/plan/tasks/`에서 번호 $ARGUMENTS의 지시서를 찾는다.
  - 없음 → **plan mode로 들어가(`EnterPlanMode`) 초안부터 쓴다.** 목적은 번호 뒤에 적은 내용 → 없으면 `docs/plan/roadmap.md` "예정"에 있는 그 번호의 제목 → 그것도 없으면 대화의 사용자 요청. 아무것도 없으면 무엇을 할지 묻는다.
    - plan 단계에서는 관련 코드와 `docs/plan/roadmap.md`·`decisions.md`·`constraints.md`(하지 않음·금지 목록)를 읽기만 하고, 아래 지시서 구성대로 계획 파일에 쓴다.
    - 사용자가 plan을 승인하면 그 내용을 `docs/plan/tasks/NNN-제목.md`(상태: `대기`)로 저장하고 브랜치를 만든 뒤 ②로. (`docs/`는 git에 올리지 않으므로 커밋하지 않는다)
  - `대기` → 그대로 시작.
  - `수정 요청` → 맨 아래 "검토 N차"만 반영한다. 테스트로 확인할 게 늘었으면 Red 목록에 추가하고 ②부터, 아니면 ③부터.
- 구성은 `docs/plan/tasks/README.md`를 따른다. 특히 **Red 목록**(테스트로 확인할 동작을 `입력 → 기대값`으로, 없으면 "없음"), **새 함수 시그니처**, **하지 말 것**, **사용자가 아이폰에서 확인할 것**을 채운다.
- 백그라운드 유지·갱신 방식을 건드리면 `docs/plan/constraints.md`를 먼저 확인한다. 거기서 막힌 방법은 지시서에 넣지 않는다.
- 브랜치: `git switch main && git pull && git switch -c task/<번호>-<이름>` (이미 있으면 `git switch`로 이어서 쓴다).
- roadmap: 그 번호를 `docs/plan/roadmap.md`의 "예정"에서 "진행 중"으로 옮긴다. roadmap에 없는 번호면 "진행 중"에 `| 번호 | 제목 |`으로 추가한다.
- `docs/`는 .gitignore 대상이라 지시서는 커밋하지 않는다.

## ② 테스트 작성 (Red 목록이 "없음"이면 건너뜀)
- `qa`를 **테스트 모드**로 호출한다. 프롬프트에 지시서 경로와 "처음 작성"을 적는다.
- 확인할 것: Red 목록 ↔ 테스트 매핑에 빠진 항목이 없는지, 실패 이유가 assertion 또는 시그니처가 적힌 새 함수의 "없는 이름"뿐인지, `git status`에 `LiveLyricsTests/` 밖 변경이 없는지.
- QA가 "지시서 모호점"을 보고하면 지시서를 고치고(커밋 없음) ②를 다시 한다.
- 커밋: `test(<scope>): ... (Red)`

## ③ 개발
- `ios-dev`를 호출한다. 프롬프트에 지시서 경로, 테스트 파일 경로, "테스트·계약 파일 수정 금지"를 적는다. 수정 반영이면 피드백 목록이나 "검토 N차"를 함께 준다.
- 확인할 것: `git status`에 수정 범위 밖 변경이 없는지(특히 `LiveLyricsTests/`, `LyricsActivityAttributes.swift`, Info.plist, `*.xcodeproj`).

## ④ 테스트 실행 (②를 건너뛰었으면 ⑤로)
- `qa`를 **테스트 모드(재실행)**로 호출한다. 실패가 있으면 아래 "피드백 처리"로.

## 피드백 처리 (④ 실패, ⑤ 지적 공통)
- 피드백 목록을 `ios-dev`에 넘긴다. 항목마다 수용/거절이 돌아온다. 수용분은 고친 뒤 ④로.
- 거절은 리드가 **지시서를 기준으로** 판정한다:
  - 테스트가 틀림 → `qa`에 판정 근거와 함께 테스트 수정을 지시
  - 지시서가 모호함 → 리드가 지시서를 고친다 (커밋 없음)
  - 개발이 틀림 → `ios-dev`에 다시 수정을 지시
  - 지적이 범위 밖 → 기각하고 보고서 "남은 이슈·질문"에 남긴다
- ③~⑤를 3번 넘게 돌면 멈추고 사용자에게 묻는다.

## ⑤ 확인과 코드 리뷰
- 리드가 직접 확인한다:
  - CLAUDE.md "명령"의 테스트 명령 → 전부 통과 (개발의 "통과" 보고를 믿지 않고 직접 돌린다)
  - `git diff --stat <Red 커밋> -- LiveLyricsTests`가 비어 있음 (리드 판정으로 QA가 고친 경우만 예외)
  - `git status` 수정 범위, `scripts/check.sh`, 빌드 명령
  - 지시서 "하지 말 것"과 diff 대조
- 커밋: `feat(<scope>): ...`
- `/code-review`를 실행한다. 지적이 있으면 "피드백 처리"로 보낸다. 반영 후 `fix(<scope>): 리뷰 반영`으로 커밋한다. 재리뷰는 하지 않는다. 기각한 지적은 PR 본문에 "보류"로 남긴다.

## ⑥ 아이폰 확인 요청
- 보고서(`docs/dev/reports/<번호>-report.md`)를 요약하고, 지시서의 "사용자가 아이폰에서 확인할 것"과 Xcode에서 할 일(실기기 실행, 필요한 설정의 클릭 경로)을 보여 준다.
- "확인한 뒤 로그를 붙여 `/judge <번호>`를 입력해 주세요"로 끝내고 **멈춘다**.
- 순수 로직만 바꿔서 지시서에 아이폰 확인 항목이 없으면, 사용자에게 알리고 `/judge`의 "통과" 처리로 바로 간다.

## 규칙
- push, PR 생성, merge 전에는 사용자 확인을 받는다.
- `git add`는 파일 이름으로만 한다(`-A`, `.`, `commit -a` 금지). `Spotify/SpotifyConfig.swift`의 Client ID 변경과 `Spotify/SpotifySecrets.swift`는 절대 스테이징하지 않는다. 커밋 전에 `scripts/check.sh`를 돌린다.
- 끝나면 에이전트 호출 수, Red 테스트 수, 피드백 루프 수, 리뷰 지적 수(반영/기각)를 한 줄로 요약한다.
