# 작업 지시서

> 작성: 리드 (Claude Code 메인 세션) · 서브에이전트(`qa`, `ios-dev`)는 **읽기만**

리드가 `qa`·`ios-dev`에게 넘기는 작업 지시서를 모아 두는 곳. 진행은 `/task N`, 판정은 `/judge N`.

## 작업 흐름

```
/task N
 ① 리드     지시서 작성 docs/plan/tasks/NNN-제목.md (상태: 대기) → 사용자 승인 → 브랜치 task/NNN-이름
 ② qa       Red 목록대로 단위 테스트 작성 → 실패 확인              (Red 목록이 "없음"이면 ②④ 건너뜀)
 ③ ios-dev  지시서대로 개발 → 빌드 → 보고서 docs/dev/reports/NNN-report.md (상태: 검토 요청)
 ④ qa       테스트 실행 ──── 실패 → 피드백 ─┐
 ⑤ 리드     재실행·check.sh·/code-review ── 지적 ─┴→ ios-dev: 수용(수정 → ④) / 거절(→ 리드 판정)
 ⑥ 리드     보고서 요약 + 아이폰에서 확인할 것 안내 → 멈춤
      ↓ 사용자: 아이폰 테스트 → "/judge N" + 로그
/judge N
 ⑦ qa       로그를 확인 항목과 대조해 근거 정리 → 리드 판정
              ├ 통과     → 상태: 완료, roadmap·decisions 갱신, PR → squash merge
              └ 수정 필요 → 지시서 맨 아래 "검토 N차 — 수정 요청" (상태: 수정 요청) → /task N
```

거절 판정: 테스트가 틀림 → `qa`가 테스트 수정 / 지시서가 모호함 → 리드가 지시서 보완 / 개발이 틀림 → `ios-dev`가 수정 / 범위 밖 → 기각

## 지시서 규칙
- 파일 이름: `011-짧은-영문-제목.md`, `012-…` 순서
- 맨 위 `상태:` 줄 하나: `대기` / `수정 요청` / `완료` / `보류`. **리드만 바꾼다**
- 구성: 목적 / 할 일 / **Red 목록** / **새 함수 시그니처** / 주의 / 하지 말 것 / 완료 조건 / 사용자가 아이폰에서 확인할 것
  - **Red 목록**: 테스트로 확인할 동작을 `입력 → 기대값`으로 적는다. 순수 로직만 (파싱, 계산, 판단 규칙). 없으면 "없음"
  - **새 함수 시그니처**: Red 목록이 아직 없는 함수를 부르면 그 시그니처 (예: `static func clean(_ title: String) -> String`). 없으면 "없음"
- 수정 요청은 지시서를 새로 만들지 않고 **같은 파일 맨 아래에 "검토 N차" 섹션을 추가**

## 보고서 규칙 (`ios-dev`가 `docs/dev/reports/`에 작성)
- 파일 이름: 지시서와 같은 번호 `NNN-report.md`
- 맨 위 `상태:` 줄: `진행 중` / `검토 요청`
- 구성: 바꾼 파일과 이유 / 빌드·테스트 결과 / 피드백 처리(항목 · 수용/거절 · 근거) / 지시서와 다르게 한 점과 이유 / 사용자가 테스트할 항목 / 남은 이슈·질문
- 수정 요청을 반영하면 같은 보고서 맨 아래에 "수정 N차" 섹션을 추가
