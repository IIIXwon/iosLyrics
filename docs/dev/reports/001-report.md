## 버튼을 누르면 (구현한 순서)
1. 로그: `▶︎ 카드 버튼 눌림 — 앱 상태 · 위치 권한 · 위치 추적 ON/OFF`
2. `Task`로 Spotify 재생 요청을 시작하고, 곧바로 위치 추적 재시작 (둘이 동시에 진행)
3. 폴링 재개(`nowPlaying.start()`), 1초 대기 후 `refreshNow()`로 즉시 조회 → 카드 갱신
4. 위치 추적을 새로 시작했다면 5초 뒤 `✅ 위치 추적 재시작 성공 — 위치 수신 N회` 또는 `❌ … 위치 수신 0회 — 백그라운드에서 시작이 막혔을 수 있어요`
- Spotify가 이미 재생 중이라 재생 요청이 403(제한)으로 거절돼도 멈추지 않고 가사만 다시 연결한다 (`ℹ️ 이미 재생 중이거나 …` 로그)

## 지시서와 다르게 한 점과 이유
1. **인텐트를 새 파일이 아니라 `LyricsActivityAttributes.swift`에 넣었다.**
   지시서는 "인텐트 타입은 앱·위젯 두 타깃에 포함"이다. 새 파일을 두 타깃에 모두 넣으려면 `project.pbxproj`를 직접 수정해야 하는데(이 프로젝트는 폴더 동기화 방식이라 새 파일은 한쪽 타깃에만 들어감), Xcode 도구에는 타깃 멤버십을 바꾸는 기능이 없다. 이미 두 타깃에 들어 있는 이 파일에 두는 것이 가장 안전하다고 판단했다. 분리하고 싶으면 Xcode에서 새 파일을 만들어 Target Membership 두 개를 체크하면 된다.
2. **재생 요청 전에 "이미 재생 중인지" 먼저 조회하지 않았다.** 지시서 순서(재생 요청과 위치 추적 시작을 먼저)를 지키려고 요청을 먼저 보내고, 403이 오면 "이미 재생 중일 수 있음"으로 보고 가사만 다시 연결한다. 403이 항상 "이미 재생 중"이라는 보장은 없으니 로그의 HTTP 본문으로 확인해야 한다.
3. **지시서에 없는 보조 변경**: `ExperimentController`를 공유 인스턴스(`shared`)로 바꿈, `SpotifyAuth.needsRelogin` 추가. 둘 다 지시서의 "앱 초기화 순서 주의"와 "재로그인 안내"를 지키기 위한 최소 변경이다.
4. 버튼은 `isPlaying == false`일 때 보이므로 **추적을 막 시작해서 재생 정보가 없을 때도** 보인다 (지시서 문구 그대로 구현).

## 사용자가 아이폰에서 테스트할 항목 (지시서와 같음 + 보강)
0. **재로그인**: 앱 화면의 Spotify 구역에 주황색 안내가 보이면 로그아웃 → 다시 로그인 (새 권한 `user-modify-playback-state` 동의 화면이 떠야 함)
1. **버튼으로 재개**: 재생 → 일시정지 → 4분 대기 → 로그에 `🔋 … 위치 추적을 껐어요` 확인, 그 직전 카드가 "⏸ 일시정지 / ▶︎를 누르면 가사가 다시 나와요"로 바뀌었는지 확인 → 화면 잠금 → 카드의 ▶︎ → 음악과 가사가 몇 초 안에 이어지는지
2. **Spotify 버튼으로 재개 후 ▶︎**: 1번처럼 4분 대기 → Spotify 잠금화면 컨트롤로 재생 → 카드가 멈춰 있는지 확인 → 카드의 ▶︎ → 가사가 이어지는지 (이때 재생 요청이 403으로 오는지도 로그로 확인)
3. **3분 안에 재개**: 일시정지 1분 후 Spotify 버튼으로 재생 → 버튼 없이 자동으로 이어지는지 (기존 동작 유지)
4. 1번이 위치 추적 시작 실패(`❌ … 위치 수신 0회`)로 안 되면 → 앱 화면의 "위치 '항상 허용' 요청"을 눌러 권한을 "항상"으로 바꾸고 1번 반복
5. 로그 전체 복사 → Claude 앱에 "001 검토해줘"와 함께 전달

로그에서 볼 표시: `▶︎ 카드 버튼 눌림`, `Spotify 재생 요청 성공/실패 (HTTP …)`, `위치 추적 재시작 …`, `위치 수신 N회`

## 질문
1. **앱이 완전히 종료된 상태에서 ▶︎를 누르면?** iOS가 앱을 새로 시작하는데, 컨트롤러 `init`은 (기존 동작대로) 남아 있던 Live Activity를 전부 종료하고 `isRunning`도 꺼진 상태라, 로그에 "추적이 꺼져 있어요 → 앱 화면을 열어 …"만 남기고 아무것도 하지 못한다. 이 경우 (a) 지금처럼 안내만 한다 (b) 새로 시작할 때 기존 카드를 종료하지 않고 이어받는다 중 어느 쪽으로 할지 정해 주세요. 이번 실험은 "일시 중단(suspended)" 상태가 대상이라 (a)로 두었다.
2. 재생 요청에 `device_id`를 넣지 않았다 (지시서에 없음). 활성 기기가 없으면 404이고 카드에 "Spotify 앱을 한 번 열어 주세요"를 띄운다. 테스트에서 이 404가 잦으면 마지막 재생 기기를 기억해 `device_id`를 지정하는 방식을 제안한다.

## 수정 1차 (2026-10-26) — 지시서 "검토 1차 — 수정 요청" 반영

상태: 검토 요청 (수정 1차 반영, 아이폰 재테스트 대기) · 빌드: BuildProject **성공**

### 1. 404 대응: 재생 기기 지정
- **기기 ID 기억**: 폴링 엔드포인트를 `GET /v1/me/player/currently-playing` → **`GET /v1/me/player`**로 바꿨다. 같은 정보에 `device`(id·name·type·is_active)가 함께 와서 **호출 수는 늘지 않는다**. 재생 중(`is_playing == true`)일 때 기기 ID를 `NowPlayingService.lastDevice`에 기억하고, 앱을 껐다 켜도 남도록 `UserDefaults`(`spotify.lastDevice`)에 저장한다. 기기가 바뀔 때만 `🔌 재생 기기 기억: 이름 (종류)` 로그.
- **▶︎ 처리 순서** (`ExperimentController.requestPlay`)
  1. `PUT /me/player/play?device_id=<기억한 ID>` (기억한 기기가 없으면 기기 지정 없이). 로그에 `HTTP …, 기기: 이름` 또는 `기기 지정 없음` 표시
  2. **404면** `GET /me/player/devices`로 목록을 받아 `🔌 기기: 이름 · 종류 · 활성 예/아니오`로 전부 로그. 목록이 비었으면 `❌ 연결된 Spotify 기기가 없어요 — Spotify 앱이 연결을 끊었음`
  3. 기억한 ID가 목록에 있으면 그 기기, 없으면 `type == "Smartphone"` 기기로 `PUT /me/player` (`{"device_ids":[id],"play":true}`) **1회 재시도** → `▶︎ 재생 기기 이전 성공 (HTTP …)`
  4. 그래도 실패하거나 옮길 기기가 없으면 지금처럼 로그 + 카드에 "Spotify 앱을 한 번 열어 주세요"
- 컴퓨터·스피커 등 스마트폰이 아닌 기기로는 재생을 옮기지 않는다 (기억한 기기가 목록에 있을 때만 예외).
- 코드: `SpotifyAPI`에 `play(deviceID:)`, `devices()`, `transferPlayback(to:play:)`, 공통 `put(...)` 추가 / `SpotifyDevice` 모델 추가 / `CurrentlyPlaying.device` 추가

### 2. 앱 상태 로그 보강
- 조회와 조회 사이가 **20초 넘게 벌어지면** 다음 조회 때 `💓 조회 재개 — 4분 12초 만에 · <앱 상태> · 위치 ON/OFF`를 남긴다. 위치 추적을 끈 뒤 앱이 실제로 중단됐는지 판단하는 용도. (10번째 조회마다 찍는 기존 `💓` 로그는 그대로)
  - 폴링 간격은 최대 5초이므로 20초 넘는 공백은 정상 상황이 아니다. 호출 한도(429) 대기나 오류 후 대기 때도 찍힐 수 있는데, 그 경우에는 앞에 `⚠️` 로그가 함께 있다.
- `scenePhase`가 background로 바뀔 때의 `📱 백그라운드로 이동` 로그는 이미 있어서 유지했다.

### 3~4. 보고서 질문 정리
- 질문 1(앱이 종료된 뒤 ▶︎): **(a) 안내만** 유지 — 코드 변경 없음
- 질문 2(device_id): 위 1번으로 반영

### 지시서와 다르게 한 점
- 없음. 다만 폴링 엔드포인트가 바뀌었으므로, `/me/player`와 `currently-playing`의 응답 차이로 곡 정보가 달라지지 않는지(특히 광고·팟캐스트 구간)는 재테스트 로그에서 확인이 필요하다. 필요한 scope(`user-read-playback-state`)는 이미 있다.
